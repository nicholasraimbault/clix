The initial implementation's passing tests did not establish safe retries,
single-use consumption, result fidelity or file conflict handling. The repairs
follow the actual failure boundaries:

- `Store::update` commits a private, synced replacement before publishing state
  in memory. A failed write poisons subsequent mutations until repair/restart.
  The daemon holds an exclusive state-directory lock. State is mode 0600 inside
  a 0700 directory. Owner access stays on the same-UID 0600 Unix socket.
- The PAKE stores Ed25519 identities and rejects ambiguous names/keys. Distinct
  authenticated commit and acknowledgement phases bind both identities. Lost
  acknowledgements report saved or possibly saved trust instead of claiming no
  pair exists. A pin conflict after pairing explicitly says trust remains saved.
- Mesh uses TLS 1.3 with pinned raw public keys in both directions, no plaintext
  fallback or resumption. Paired identity determines the caller. Owner mutations
  and legacy result-injection messages are rejected. Network loss is retriable;
  failed authentication does not become a waiting/successful connection.
- One execution acceptance transaction creates the running job and reserves its
  once grant before spawn. Duplicate IDs must match the invocation. Production
  uses asynchronous direct process execution; there is no shell wrapper.
  Completion stores exact bytes and the real exit status. Capture failure does
  not discard a known successful exit when consuming a once grant.
- One dispatcher retries durable remote jobs and permission deliveries after
  restart. Runner restart makes previously running jobs uncertain, without
  automatic re-execution. Request receipts survive owner decisions so a lost
  acknowledgement cannot recreate the same prompt.
- Pin uses content/mode manifests and per-peer baselines, including deletions.
  Relative operations use opened directories and reject symlinks. Publication
  checks expected versions, retains displaced inodes and durable receipts, and
  stops on incomplete recovery or later writes to retained inodes. It does not
  overwrite an actively granted executable. The owner must review recovery;
  there is no automated merge or recovery policy.
- Persisted requests drive notifications and the tray. Production notify-rust
  receives and applies native actions to the same objects as the CLI. Local
  owner controls do not depend on Tailscale startup. CLI tool resolution uses
  the invoking owner's PATH/cwd; log output includes IDs and escaped argv.
  Install waits for the owner RPC to become ready.

The code is fit to keep as the tested core. Its limits are concrete: the
whole-state JSON store copies and rewrites retained results, pin scans are
synchronous and bounded, and recovery is manual. Those choices are understandable
for the present small deployment; they are not evidence of scale or long-lived
operation. Do not replace these limits with undocumented success claims.

## Recovery and unfinished work

If a job is uncertain, inspect the actual tool/system before regranting it.
Replacing the grant is an owner decision; it does not establish whether the old
command took effect.

A pin recovery receipt names the original relative path, expected/replacement
fingerprints and retained version filename. Stop syncing while resolving it.
Review the live path and retained version locally on the affected machine;
restore/copy the desired contents before removing the reviewed receipt and its
retained version together. Removing a receipt alone is acknowledgement of that
owner decision, not an automatic merge. There is no recovery command or garbage
collector yet.

[Current work](current.md) is the verdict and authoritative outstanding list:
same-UID agent authority, global log coverage, physical sleep, desktop UX,
continuous replication and operational scale. No two-Arch or full-v0 completion
claim is made.
